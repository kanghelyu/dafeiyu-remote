# Dafeiyu Virtual Display Driver (IddCx / UMDF2) — phase-1 skeleton

**Status: design + skeleton only.** Nothing in this directory is built or shipped by
`cargo build`. The user-mode half of the protocol *is* implemented and tested:
[`../src/win_driver.rs`](../src/win_driver.rs). This directory is the kernel-adjacent half:
an IddCx **indirect display driver** (UMDF 2), its INF, and the build/signing/install runbook.

Why a driver at all: on Windows there is no user-mode way to add a real extended desktop.
`IddCx` (Indirect Display Driver Class eXtension) is what SudoVDA, RustDesk and UU
GameViewer all use, and it is the only mechanism Microsoft supports for a
non-hardware-attached monitor. A virtual display is therefore a PnP device + a UMDF
driver, and the agent talks to it over IOCTLs (see "Protocol" below).

Everything here is **written from scratch** for this project (PolyForm Noncommercial License 1.0.0). The
Microsoft `IddSampleDriver` sample and SudoVDA (MIT) were read for structure and to confirm
API usage only; no code was copied, and the protocol numbers are deliberately our own so
both drivers can coexist on one machine.

## 2. Version layering: IddCx 1.2 now, 1.10 later — read this before touching the INF

Two IddCx versions matter:

* **IddCx 1.2** (`UmdfExtensions=IddCx0102`, Windows 10 1809+). Supports everything phase 1
  needs: adapter init, monitor create/arrival/departure, dynamic mode tables via
  `IddCxMonitorUpdateModes` (`IDARG_IN_UPDATEMODES`), per-monitor swap chains. No HDR.
* **IddCx 1.10** (Windows 11 22H2 *September 2023 update*, build 22621.2359+). Adds HDR
  (`IDDCX_TARGET_MODE2`, `IddCxMonitorUpdateModes2`, `IDARG_IN_UPDATEMODES2`) and
  `IddCxMonitorSetDefaultHdrMetaData`.

The phase-1 target is **IddCx 1.2**, matching the two shipped indirect display drivers we
reverse-engineered (UU / RustDesk both declare `IddCx0102`) and keeping the Windows 10
installed base. `IddCxMonitorUpdateModes2` **cannot** be called from a 1.2 extension; if we
declare `UmdfExtensions=IddCx0110` the extension will not load on anything below build
22621.2359, including plain Windows 11 21H2 and most 22H2 machines.

HDR plan (phase 2, not now):

1. Keep `IddCx0102` as the shipped INF so nothing regresses.
2. Build a second driver binary against the 1.10 DDIs, and ship a second INF whose
   `[Manufacturer]` model section is decorated for the newer OS (e.g.
   `NT$ARCH$.10.0...22621`); our installer picks the variant from the OS build, because
   INF OS decorations cannot express a patch-level requirement.
3. Resolve the 1.10-only exports by hand (`IddCxGetVersion`,
   `GetProcAddress(IddCx.dll, "IddCxMonitorUpdateModes2")`) if one binary must serve both
   OS families, and gate on the version returned at `EvtIddCxAdapterInitFinished`.

Consequence for the mode-update path in this skeleton: `driver.c` calls
`IddCxMonitorUpdateModes` (1.2). The 1.10 call sites are marked `// V2:`.

## 3. Callback map (what the finished driver must do)

| Callback (or API) | Responsibility | Skeleton state |
|---|---|---|
| `DriverEntry` | `WdfDriverCreate`, register `EvtDeviceAdd`, WPP init | written |
| `EvtDeviceAdd` | `WDF_PNPPOWER_EVENT_CALLBACKS`, `IDD_CX_CLIENT_CONFIG_INIT`, wire every `EvtIddCx*`, `IddCxDeviceInitConfig`, `WdfDeviceCreate` (device context), `IddCxDeviceInitialize`, create the device interface for `{54EC77FA-…}` | written, TODOs |
| `EvtDeviceD0Entry` | lazily `InitAdapter` once per boot | written |
| `InitAdapter` | `IDDCX_ADAPTER_CAPS` (MaxMonitorsSupported=8, `EndPointDiagnostics`), `IddCxAdapterInitAsync` | written |
| `EvtIddCxAdapterInitFinished` | store `IDDCX_ADAPTER`, start the control thread | written |
| `EvtIddCxDeviceIoControl` | our control plane: create/update/destroy/list/take-event/protocol-info (IddCx redirects `IRP_MJ_DEVICE_CONTROL` here; the plain `EvtIoDeviceControl` never fires) | written |
| `EvtIddCxParseMonitorDescription` | validate the EDID we generated, return monitor description | skeleton |
| `EvtIddCxMonitorGetDefaultDescriptionModes` | preferred + fallback modes for a brand-new monitor | skeleton |
| `EvtIddCxMonitorQueryTargetModes` | current mode table for that connector (the table `UPDATE` mutates) | skeleton |
| `EvtIddCxAdapterCommitModes` | accept OS mode choice; no swap-chain work here | written (no-op) |
| `EvtIddCxMonitorAssignSwapChain` | start a per-monitor worker: `IddCxSwapChainSetDevice`, loop `IddCxSwapChainReleaseAndAcquireBuffer`, hand the surface to the frame path, `IddCxSwapChainFinishedProcessingFrame` | skeleton with real loop shape |
| `EvtIddCxMonitorUnassignSwapChain` | stop the worker; on exit `WdfObjectDelete((WDFOBJECT)hSwapChain)` so the OS rebuilds it | skeleton |
| `EvtIddCxMonitorDeparture` path | on `DESTROY`: `IddCxMonitorDeparture`, delete monitor object and context | skeleton |

Mode/table ownership: the mode table lives in the **driver**, per connector, and is only
mutated by `CREATE`/`UPDATE`; the OS is told via `IddCxMonitorUpdateModes` and then runs its
normal CCD commit. This is exactly why "remote resolution change does not touch physical
monitors": the physical outputs' paths are never in the target list.

## 4. Protocol (must match `../src/win_driver.rs` byte for byte)

Device interface class GUID `{54EC77FA-1377-44E6-8C32-88FD5F44C84C}` (the class GUID the
RustDesk/UU indirect display driver also publishes; our *device instance* path is
`\\?\root#dfyvdisplay#…`, so the two drivers are distinguishable but existing tooling that
looks up the class GUID keeps working).

All IOCTLs are `CTL_CODE(FILE_DEVICE_UNKNOWN, 0x800+n, METHOD_BUFFERED, FILE_ANY_ACCESS)`:

| IOCTL | Value | Input | Output |
|---|---|---|---|
| `IOCTL_VDISPLAY_CREATE` | `0x222000` | `VDISPLAY_CREATE` (80 B) | `UINT32` id |
| `IOCTL_VDISPLAY_UPDATE` | `0x222004` | `VDISPLAY_UPDATE` (20 B) | — |
| `IOCTL_VDISPLAY_DESTROY` | `0x222008` | `VDISPLAY_DESTROY` (4 B) | — |
| `IOCTL_VDISPLAY_LIST` | `0x22200C` | — | `VDISPLAY_STATE_LIST` (200 B) |
| `IOCTL_VDISPLAY_TAKE_EVENT` | `0x222010` | — | `VDISPLAY_EVENT` (8 B) or 0 B |
| `IOCTL_VDISPLAY_GET_PROTOCOL_INFO` | `0x222014` | — | `VDISPLAY_PROTOCOL_INFO` (8 B) |

Hotplug notification: the driver creates the auto-reset named event
`DafeiyuVDisplayDeviceEvent` and signals it when a monitor arrives/departs or a mode table
changes; it also queues `VDISPLAY_EVENT {kind,id}` records drained by
`IOCTL_VDISPLAY_TAKE_EVENT`. The event is an optimization — `LIST` is authoritative.

`static_assert(sizeof(...) == ...)` in `driver.h` is the compile-time guard for the shared
ABI; the Rust side asserts the same numbers in unit tests. Bump `PROTOCOL_VERSION` (Rust)
and `DFY_VDISPLAY_PROTOCOL_VERSION` (C) together on any change.

## 5. Build (WDK, not part of the cargo build)

Prerequisites, one-time:

1. Visual Studio 2022 with the "Desktop development with C++" workload.
2. **Windows Driver Kit 10.0.26100** or newer (installs the *Windows Driver Kit* extension for
   VS and the `msbuild` driver targets). The offline EWDK ISO is an alternative for CI.
3. Optional: `Inf2Cat`, `stampinf`, `signtool`, `devcon` from the WDK/SDK `bin` folders.

Commands (`build.bat` runs these; `Makefile` is the `nmake` wrapper):

```bat
:: 1. project file is still missing - generate from the WDK "WDM Driver" template,
::    then keep these properties: TargetName=dfy-vdisplay, DriverType=UMDF,
::    ConfigurationType=DynamicLibrary, WDK include path, /W4 /WX
set WDK=10.0.26100.0

:: 2. compile the UMDF driver DLL
msbuild dfy-vdisplay.vcxproj /p:Configuration=Release /p:Platform=x64 /p:WDKVersion=%WDK% /m

:: 3. stamp DriverVer into the INF (build number/hash come from CI)
stampinf -f dfy-vdisplay.inf -d * -v 0.1.0.*

:: 4. produce the catalog and sign the package
Inf2Cat /driver:. /os:10_X64,10_ARM64
signtool sign /fd sha256 /a /f <cert.pfx> /tr http://timestamp.digicert.com /td sha256 dfy-vdisplay.cat
```

Not building here: this checkout has no WDK and the skeleton has TODO bodies on purpose.
First build milestone = compile clean at `/W4 /WX` with the TODO bodies stubbed to return
`STATUS_NOT_IMPLEMENTED`, then implement incrementally behind the protocol.

## 6. Install / uninstall (elevated shell)

```bat
:: install (dev, driver package must already be test-signed, see §7)
pnputil /add-driver dfy-vdisplay.inf /install

:: verify
pnputil /enum-drivers | findstr /i dafeiyu
devcon status Root\dfyvdisplay
Get-PnpDevice -FriendlyName "*Dafeiyu*"     :: PowerShell

:: uninstall
devcon remove Root\dfyvdisplay
pnputil /delete-driver oem<nn>.inf /uninstall /force
```

Root-enumerated device ids: `devcon install dfy-vdisplay.inf Root\dfyvdisplay` also works
and is what the installer will shell out to (or we use `SetupDiCreateDeviceInfo` +
`DiInstallDevice` from Rust, which avoids shipping `devcon.exe`).

After install the agent must see the interface:
`crates/dfy-vdisplay/src/win_driver.rs::enumerate_device_interfaces()` returns
`\\?\root#dfyvdisplay#…#{54ec77fa-…}`; if it returns an empty list, the driver did not start
(check `Device Manager → Display adapters`, UMDF host events in
`Microsoft-Windows-User-Mode Driver Framework`).

## 7. Signing and distribution

| Stage | What is needed | Lead time | Notes |
|---|---|---|---|
| Dev loop | `bcdedit /set testsigning on` + reboot; self-signed cert in `Trusted Root`/`Trusted Publishers`; sign `.cat` | minutes | Secure Boot must be off, or use test-signing-aware boot; **only on dev machines** |
| Internal beta | EV code-signing certificate (HSM/token), sign catalog + timestamp | days (cert issuance days–weeks) | EV cert is the prerequisite for the next row, buy early |
| Public release | **WHQL/attestation signing** via Partner Center: EV cert → HLK Studio (Indirect Display playlists, D3D, PnP) → submit `.hlkx` → Microsoft-signed catalog | **2–4 weeks calendar time** (queue + failures) | Cannot be bypassed: an unsigned/unattested display driver will not load on modern Windows with Secure Boot |
| Auto-install | ship `dfy-vdisplay.cat` + `.inf` + `dfy-vdisplay.dll`, install as SYSTEM via our service | — | driver update = new package version, `pnputil /add-driver` then restart device |

Risk: WHQL for a display driver is stricter than a plain driver (display class + Indirect
Display tests). Budget the 2–4 weeks as calendar time, not engineering time — it is the
reason the plan front-loads an internal test-signed build for milestone M4.

## 8. Kernel-risk notes (what can bluescreen, and the mitigations we will implement)

A UMDF display driver runs the IddCx callbacks in `WUDFHost.exe` (user mode) but the
`IndirectKmd` filter runs in kernel; a callback that blocks, re-enters or leaks a monitor
object can bugcheck the machine.

* **Blocking in an IddCx callback**: no waits, no `DeviceIoControl` round trips, no
  `KeWaitForSingleObject` in *any* `EvtIddCx*` callback. The swap-chain loop belongs in a
  dedicated worker thread; `EvtIddCxMonitorAssignSwapChain` only stores state and starts it.
* **Swap-chain lifetime**: never touch the swap chain after
  `EvtIddCxMonitorUnassignSwapChain`; the worker's last act is closing the handle and
  `WdfObjectDelete((WDFOBJECT)hSwapChain)` so the OS can rebuild it. A thread that keeps
  using a deleted swap chain after monitor removal is the #1 crash in this class of driver.
* **Request lifetime**: `EvtIddCxDeviceIoControl` requests must be completed exactly once
  (`WdfRequestComplete`), and only after the response buffer is valid. Keep the handler
  synchronous (our IOCTLs are microseconds) ; if a future call needs to wait, forward the
  request instead of blocking.
* **Object referencing**: monitor context owns nothing that outlives its `IDDCX_MONITOR`;
  the adapter context owns the mode tables. Surviving a driver unload with a pending worker
  ⇒ `WdfObjectDelete` it in `EvtCleanupCallback`.
* **IRQL**: everything in the swap-chain worker is `PASSIVE_LEVEL`; no spinlocks around D3D.
* **What actually bugchecks** in practice: `DRIVER_POWER_STATE_FAILURE` (worker not stopped
  on D0-exit/S3), `SYSTEM_THREAD_EXCEPTION_NOT_HANDLED` (worker AV after swap-chain
  teardown), `IRQL_NOT_LESS_OR_EQUAL` (touching pageable data from a DPC). Every teardown
  path in `driver.c` is written with a stop event + join, not "just unload".

Observability: WPP/ETW (`Trace.h`, `DoTrace`), a driver-owned ring buffer of the last 64
protocol events exposed through `IOCTL_VDISPLAY_TAKE_EVENT` for field debugging, plus
`WdfVerifier` and `!wdfkd.wdflogdump` during bring-up. `tracefmt`/`traceview` from the WDK
serve the WPP side; do not put `DbgPrint` in the frame path.
